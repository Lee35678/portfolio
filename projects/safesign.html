협업 방식

서비스별 브랜치에서 개발해 dev 브랜치로 모았고, 서비스 사이 데이터 형식은 코드보다 먼저 계약으로 정했습니다.

계약을 먼저 정하고 나눠서 개발

팀 저장소를 처음 만들 때 서비스 4개의 뼈대와 서비스 사이에 주고받을 데이터 형식(JSON 스키마 4종)부터 정했습니다. 덕분에 4명이 각자 다른 서비스를 동시에 만들 수 있었습니다.

서비스별 브랜치와 통합 브랜치

vision·web·actuation·picar·data를 각자 기능 브랜치에서 만들고 dev 브랜치에 모았습니다. 4개 서비스의 1차 통합 병합을 맡았습니다.

테스트로 작업을 넘겨받기

팀원이 응답 판정 기준표와 인수 테스트 22개를 먼저 쓰고, 그 테스트를 통과하는 코드를 구현했습니다. 목표일보다 이틀 빠르게 병합됐습니다.

실험은 운영 코드와 분리

딥러닝 비교 연구는 별도 브랜치에서 진행하고 dev에 병합하지 않았습니다. 결론만 문서로 옮겨 운영 코드에 섞이지 않게 했습니다.

결정은 근거와 함께 기록

회의 자료마다 선택지·근거 수치·권고를 붙였고, 안건별 결정권자를 정해 결정을 기록했습니다. 화면 디자인을 바꿀 때도 화면 흐름과 기능 계약은 그대로 두어 팀원이 만든 테스트가 계속 통과하게 했습니다.

트러블슈팅

  1. 09.20 – 21

    정답률 98.81%는 허수였다

    원인
    공개 데이터 27,735건 중 97.7%가 805개 연속 촬영 세션에 묶여 있었습니다. 무작위로 나누면 같은 장면으로 학습하고 시험하는 셈이었습니다.
    조치
    파일명에서 세션 키를 만들어 세션 단위 GroupKFold를 기본 분할로 고정했습니다.
    결과
    실제 실력 77.57%에서 다시 출발해, 좌표 63차원을 관절 특징 23차원으로 바꿔 88.68%까지 올렸습니다.
  2. 09.22

    웹캠 정답률 28.2%, 틀린 건 모델이 아니라 측정 도구

    원인
    직접 만든 진단 도구가 키를 누른 뒤 다음 키까지 수백 프레임을 같은 라벨로 기록해, 손을 바꾸는 중간 프레임이 섞였습니다.
    조치
    이전 모델로 같은 프레임을 다시 판정해(26.0%) 모델 변경이 원인이 아님을 먼저 확인하고, 카운트다운 뒤 3프레임만 찍는 촬영 도구를 새로 만들었습니다.
    결과
    다시 찍은 105프레임 전부 정답이었습니다. 중간에 한 잘못된 진단도 보고서에 그대로 남겼습니다.
  3. 09.22

    모르는 손 모양을 확신하며 틀리는 문제

    원인
    분류기 확률은 7종 안에서 합이 1이라, 낯선 손도 가장 비슷한 클래스에 높은 값이 나옵니다. 한 클래스를 빼고 잰 측정에서 77.3%가 확신도 0.90 이상으로 오판됐습니다.
    조치
    판정 뒤에 "그 클래스에 속하기는 하는가"를 보는 소속 게이트(클래스 중심 코사인, 클래스별 임계)를 추가했습니다.
    결과
    모르는 자세 75.0% 차단, 정상 입력 오거부 2.9%. 7종이 아닌 자세의 19%가 아직 통과한다는 한계도 함께 기록했습니다.
  4. 09.22 – 23

    딥러닝으로 바꿔야 하나: 같은 조건 비교 연구

    비교
    합성 negative 클래스, Evidential Deep Learning(MLP), 관절 21개를 토큰으로 보는 HandFormer + EDL 5개 앙상블(Colab T4 178분)을 세션 단위 학습·검증·시험 분할로 운영 방식과 비교했습니다.
    결과
    분류는 동률(운영 방식 97.28%, 딥러닝 96.94%), 처음 보는 손 거르기는 운영 방식이 앞섰습니다(AUC 0.968 대 0.934). 그래서 SVM + 소속 게이트를 유지했습니다.
    실수
    연구 도중 딥러닝 설정을 KPI 촬영 데이터로 고른 것을 스스로 찾았습니다. 그 데이터로 고른 모델과 코드를 모두 지우고, 공개 데이터 안에서만 분할을 다시 짜서 비교를 처음부터 다시 했습니다.
  5. 09.29

    외부 촬영 61.4%, 일부만 빼지 않고 전부 버렸다

    원인
    외부인 70시도 중 20테이크가 정의와 다른 손 모양이었습니다.
    조치
    틀린 20테이크만 빼면 결과를 본 뒤 데이터를 고르는 셈이 됩니다. 팀 결정으로 전체를 폐기하고 팀원 3명이 RPi5 카메라로 210시도를 다시 찍었습니다.
    결과
    새 데이터로 판정 성능 5개를 확정했습니다. 손을 오른쪽으로 기울이면 과하게 거부하는 새 약점도 찾아 기록했습니다.

시스템 쪽 기여

  • 장치 호출 순서를 바꿔, 판정 뒤 picar·micro:bit 반응이 약 0.85초 늦던 구조를 없앴습니다. 팀원이 발견한 문제를 받아 결정하고 반영했습니다.
  • 직접 구현한 시행 로그 CSV가 판정 지연 KPI 2개의 원본 데이터가 됐습니다.
  • picar가 움직이면 카메라도 같이 움직이는 문제를 찾아, 카메라 보드(RPi5)와 주행 보드(RPi4B) 2대 구성을 문서와 구성 파일에 반영했습니다.
  • 교육장 기기에서만 되던 가입·수료증 재발급을 위해 같은 회원 DB를 쓰는 회사 웹사이트를 제안·구현했습니다.
